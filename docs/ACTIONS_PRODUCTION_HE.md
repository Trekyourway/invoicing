# YOURWAY | הפקת קבלות אמיתיות דרך GitHub Actions, ללא Hostinger ו-MySQL

מעודכן ל-20.11.2026.

## מה הותקן
- קוד ציבורי ב-`Trekyourway/invoicing`, ללא פרטי לקוחות. בקשות נשמרות בתיקיית `requests/` רק כקובץ מוצפן באלגוריתם AES-256-GCM + RSA-OAEP-256.
- בקשה מוצפנת נוצרת אך ורק אחרי אישור בעלת העסק שהכסף התקבל ואישור מפורש להפיק קבלה.
- שינוי בקובץ מוצפן ב-`main` מפעיל GitHub Actions. Node.js פועל על GitHub runner זמני בלבד, אין שרת Hostinger.
- לפני יצירת מסמך, ה-Action שומר reservation עם שם קובץ HMAC שאינו חושף כתובת מייל, סכום או שם לקוח. אין retry אוטומטי לאחר ניסיון תקשורת ל-HYP.
- HYP Production API `createDoc` מפיקה קבלה מסוג 400 ושולחת מייל לכתובת הלקוח באותה קריאה (`dont_send_email: 0`).
- תוצאות סטטוס ציבוריות כוללות רק `ISSUED` / `RECONCILE_WITH_HYP`, ו-`email_acknowledged`; **לעולם** לא שם לקוח, אימייל, סכום, מספר מסמך, קישור למסמך, מפתח API או פרטי תשלום.
- גיבוי PDF מומלץ באמצעות התכונה המובנית של HYP ל-Google Drive. גיבוי אוטומטי זה עדיין דורש אישור הפעלה בהגדרות החשבון.

## הפעלה ראשונה (שתי הגדרות בלבד)

1. **מפתח Production של HYP:** GitHub Actions קורא `HYP_PRODUCTION_API_KEY`. חובה להכניס **מפתח API פרודקשן אמיתי**, מתוך מסך API בחשבון HYP. המחרוזת שהופיעה בקישור PayPal IPN אינה מפתח API: ניסיון בדיקת DEMO עם אותו מזהה נכשל ונשלחה הודעת שגיאה. אין להעתיק ערכי PayPal IPN. את המפתח הנכון שומרים תחת `HYP_PRODUCTION_API_KEY` בלבד. אין לשמור מפתחות בקוד ציבורי.
2. **מפתח פענוח פרטי:** להוריד את קובץ הטקסט שמסר העוזר, לפתוח GitHub > Settings > Secrets and variables > Actions > New repository secret, להדביק את התוכן בדיוק תחת השם `RECEIPT_PRIVATE_KEY_B64`, ולשמור. זה אינו מפתח HYP. המפתח הציבורי התואם כבר בקוד.

לינק ישיר להגדרות Secrets: `https://github.com/Trekyourway/invoicing/settings/secrets/actions`.

## איך מוציאים קבלה
1. בעלת העסק מבקשת מהעוזר: "הפקי קבלה על תקבול שכבר קיבלתי" ומוסרת שם לקוח, אימייל, סכום, תאריך התקבול, אמצעי התשלום, תיאור השירות; עדיף גם אסמכתא ייחודית לעסקה. נדרש אישור מפורש שהכסף התקבל ושליחת הקבלה.
2. העוזר יוצר בקשה מוצפנת עם **המפתח הציבורי בלבד**, מעלה את הקובץ אל `requests/<uuid>.enc.json` באמצעות GitHub connector. **לעולם לא להעלות JSON גלוי.**
3. `Issue confirmed real receipts via HYP` ב-Actions מתחיל אוטומטית, שומר reservation, מפיק קבלה ב-HYP ושולח ללקוח. בודקים שהתוצאה `ISSUED` ו-`email_acknowledged=true`.
4. את המסמך הרשמי בודקים גם בלוח המסמכים של HYP. אם מייל נכשל, בודקים שם ולא מפיקים קבלה כפולה. קבלת דמו 30964 אינה חלק מפרודקשן.

## מצבי כשל
- חסר Secret: ה-Action נכשל לפני יצירת reservation ולפני פנייה לספק.
- מפתח HYP לא בתוקף, מנוי API לא מאושר או שגיאת API: status `RECONCILE_WITH_HYP` נשאר חסום, בלי ניסיון הנפקה עיוור נוסף.
- כשל רשת אחרי POST: status `RECONCILE_WITH_HYP`, בודקים קודם בלוח HYP אם קבלה נוצרה.
- שתי בקשות על אותו תקבול: HMAC מזהה מקור שווה ומונע הנפקה כפולה. אם אין אסמכתא, משתמשים בטביעת אצבע של אימייל, סכום, תאריך ואמצעי תשלום; במקרה של שתי העברות זהות באותו יום צריך אסמכתאות שונות.
- שינוי או חידוש מפתח הפענוח מחייב תכנון מעבר: בקשות שכבר הוצפנו עם הציבורי הקודם לא ניתנות לפענוח עם המפתח החדש. אין לשנות ללא בדיקת הקבלות הקודמות.

## מה עוד לא אוטומטי
- **Google Sheets** כמסך CRM/מעקב אינו נדרש להנפקה. אפשר לשמור בו תצוגה פרטית לפי צורך, אך אין חיבור API מאומת בין GitHub Actions ל-Sheets עדיין. HYP היא מקור המסמכים המחייב.
- **Google Drive**: המסמך לדוגמה הועלה קודם ידנית ונבדק. פרודקשן צריך חיבור גיבוי מובנה מ-HYP, אחרת אין הבטחה שה-PDF יגובה אוטומטית ב-Drive.
- **Grow/webhook** ושילוב AI עצמאי ללא צ'אט הינם שלב ג' עתידי; אינם תנאי לשלב הנפקת קבלה לפי הוראה מפורשת בצ'אט.
- **תנאי שחרור:** לפני קבלה אמיתית ראשונה יש לוודא ב-HYP שהחשבון הפעיל שייך לעוסק הפטור הנכון, שיש מנוי/הרשאת API Production ופרטי המסמך תקינים. אל תפיקו נתוני ניסיון על חשבון פרודקשן.
