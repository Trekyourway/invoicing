# YOURWAY Invoicing — חזון ושלבי מימוש מחייבים
עודכן: 20.11.2026 | מסמך מוצר; אין לראות בו אישור להפעלת מערכת ייצור.

## עיקרון המוצר
מנוע הפקת קבלות יחיד: מקור הבקשה -> חילוץ/קבלת שדות -> ולידציה והתאמת לקוח -> מניעת כפילויות -> HYP API (קבלה לעוסק פטור) -> HYP שולחת במייל -> סטטוס הפקה + גיבוי ל-Drive פרטי. HYP היא מקור האמת החשבונאי; MySQL משמש לניהול פעולות/לוג תפעולי, ולא כספר הכנסות חלופי.

## א׳ — "תוציא לי קבלה" דרך AI
**קלט:** בקשת טקסט, הודעה קולית מתומללת או צילום עסקה, מתוך סוכן AI שיכול להפעיל HTTPS API מאומת. לדוגמה: "קיבלתי מזוהר 400 ₪ בביט על שיעור AI, תשלח קבלה".
**פלט:** קבלה ב-HYP, בקשת שליחתה לכתובת המייל של הלקוח, זיהוי מספר המסמך וסטטוס גיבוי; הודעה למשתמשת מה קרה ולא רק "בוצע".
**שדות:** שם לקוח, כתובת מייל, סכום/מטבע, תאריך תקבול, אמצעי תשלום, תיאור, מזהה בקשה חד-חד-ערכי. השלמת כתובת מייל רק מרשומה קיימת שאומתה; לא להמציא מייל או תאריך. שאלת הבהרה אחת רק אם שדה חובה חסר.
**הרשאה:** הבקשה המפורשת של בעלת העסק להפיק קבלה היא אישור שהתקבול אכן התקבל. לא נדרש חיבור ל-Bit/PayBox/בנק, לא נדרש צילום ולא נדרש אישור שני.
**טכנולוגיה:** API מאובטח על Hostinger Node.js; סוכן ה-AI מתרגם בקשת טקסט/קול/תמונה לשדות ויכול לקרוא ל-API. תמלול/ראייה ממומשים בשכבת ה-AI, לא ב-HYP. חיבור ChatGPT לא הוגדר; אין לטעון שאפשר להפעיל את האוטומציה מהצ'אט עד חיבור Action/connector מאומת. במסך הנייד אפשר להפיק קבלה גם ללא Agent.
**תנאי השלמה:** בקשת הדגמה עם טקסט, צילום וקול כל אחת מפיקה בדיוק מסמך DEMO אחד (עם פרטים נכונים), מייל דמו התקבל ונמצא PDF. אין לייצר מסמך פרודקשן על תשלום פיקטיבי.

## ב׳ — "זורקת תמונה לתיקייה"
**קלט:** צילום מסך/תמונה/PDF לתיקיית Google Drive פרטית או העלאה ממסך נייד.
**שלבים:** אירוע/סריקה -> OCR/חילוץ AI -> רישום טיוטה עם מקור קובץ ומזהה -> הצלבת סכום, תאריך, לקוח, תיאור ומייל (אחרונים מתוך מאגר לקוחות מאומת) -> בדיקת כפילות ותנועות לא עסקיות -> הפקת קבלה באמצעות אותו מנוע מא׳ -> סטטוס ועותק פרטי.
**כלל החלטה:** העלאה יזומה של בעלת העסק יכולה לשמש הוראת הפקה רק כשהחילוץ מהימן, הנתונים מלאים ואין אזהרת כפילות. חוסר ודאות/סתירה/תנועה פרטית עוצרים לבדיקה ממוקדת; אין "אימות בנק" מומצא. צילום אינו כשלעצמו ראיה שהבנק אישר סופית תשלום, ואין להסיק ממנו מידע שלא מופיע.
**מצב קוד:** קיימים סריקת Drive וחילוץ AI לטיוטה; עדיין אינם מחוברים להנפקה אוטומטית, ולא נבדקו עם Google OAuth/מסמך אמיתי.

## ב.1 — דוח והעברה לרו״ח
**עדיפות:** להשתמש ביכולות HYP/EasyCount הקיימות, לא לפתח ספר תקבולים מקביל. לפי התיעוד: דוח הכנסות, ייצוא אקסל, דוח תקופתי אוטומטי במייל לרו״ח, העתק מכל מסמך למייל נוסף, וממשק רו״ח ייעודי עם הרשאות.
**מה כן ננהל:** מזהה תקבול, מקור פעולה, מזהה קבלת HYP, מייל נשלח/לא ידוע, גיבוי PDF ובקרת הפרשים (תקבול ללא מסמך, מסמך ללא גיבוי), ללא שינוי ערכים חשבונאיים מתוך המערכת שלנו.
**תנאי השלמה:** בדיקה בחשבון HYP שהדוח והתזמון אכן זמינים במסלול שנרכש, הגדרת רו"ח וייצוא דוגמה. עד אז אין להבטיח שהוגדר ונשלח דוח בפועל.

## ג׳ — תשלום -> קבלה ללא מגע יד אדם
**קלט:** תשלום דרך Grow או ספק סליקה אחר עם webhook/API עסקאות רשמיים (לא תשלום אישי נכנס ישירות לאפליקציית Bit/PayBox).
**תהליך:** קישור תשלום -> אישור עסקה מהשרת המאומת של ספק הסליקה -> אימות סטטוס סופי ופרטי העסקה -> מניעת כפילות באמצעות מזהה עסקה אצל הספק -> מנוע הפקת הקבלות -> מייל HYP -> Drive/רו״ח.
**חריגים:** webhook כפול, החזר/ביטול, כשל API, חוסר מייל, אי-התאמה בין סכומים; כל אלה עוברים לטיפול/התאמה ולא יוצרים מסמך שני. ב-Grow נדרש טיפול בהודעת server-to-server ובקריאת ApproveTransaction לפי חוזה הספק; חוזה האבטחה יתועד לפני הפעלה.
**חובה למנוע כפילות חשבונאית:** לפני הפעלת HYP לבדוק האם Grow/ספק אחר כבר מנפיק קבלה אוטומטית, ולבחור מנפיק אחד בלבד לכל עסקה. אם Grow מנפיק מסמך, לא לקרוא שוב ל-HYP להפקת אותו מסמך.
**שלבי הפעלה:** אחרי הצלחה עם א׳ וב׳; onboarding Grow, מזהים מסחריים, הרשאות, עמלות, sandbox מתאים ואישור production יכולים להיות תלויים בספק/חשבון.

## ארכיטקטורה לטווח ארוך
- קוד ציבורי ב-`Trekyourway/invoicing`, Secrets ב-Hostinger בלבד; בדיקות GitHub Actions אינן פועלות עם מפתחות פרודקשן.
- Hostinger Business Node.js + MySQL פרטי, HTTPS; API עם הרשאות וזהות פונה. אם מחברים סוכן חיצוני, נותנים לו Credential מוגבל במקום להעביר token מנהל לשיחה.
- HYP (קבלה רשמית ודיוור) + גיבוי Drive; רואה חשבון דרך HYP.
- לא מוסיפים נפרד Google Sheet מחייב לצורכי הנהלת חשבונות בלי לזהות צורך שאינו מכוסה ב-HYP. ניתן להוסיף יומן תפעולי/יצוא אם נדרש לבקרה.

## מדדי קבלה לפני מעבר לפרודקשן
1. `npm test` ובדיקות אבטחה/מניעת כפילויות עוברות.
2. HYP DEMO: הפקת קבלה מתאימה ומייל דמו שהגיע בפועל, כולל תוכן PDF מדויק.
3. מסד MySQL חי ב-Hostinger ופריסת HTTPS; בקשה חוזרת לאחר timeout לא מנפיקה כפול.
4. מסמכים ונתונים אמיתיים לא נחשפים ל-GitHub ציבורי, ל-Action logs או לכתובות חיצוניות בלתי מאומתות.
5. גיבוי Drive עובד, דוחות רו"ח זמינים ונבדקו בחשבון HYP.
6. Only then: API production key בתוכנית פעילה, הגדרות עוסק פטור מאומתות, הרצת עסקה אמיתית באישור בעלת העסק.
